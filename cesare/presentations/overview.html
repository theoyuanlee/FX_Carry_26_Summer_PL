The point

Before this package, five people had five different baseline carry strategies. An overlay tested on one of them told you nothing about whether it would work on another — so no extension in the project was comparable to any other. Now every extension changes one argument and inherits the same validated book underneath. The comparison, not the code, is the deliverable.

1The goal — why one base

The problem was not that anyone's code was wrong. It was that each baseline made different choices, so differences in results measured the baselines rather than the ideas.

What is in the folder

config.pyStrategyConfig — every knob, with the published baseline as the defaults. Presets ALL / G10 / EM; .with_() derives a variant.
core.pyrun(config) → StrategyResult. Orchestration only — it fixes the order of operations and adds no financial maths of its own.
fx_utils.pyThe engine: ~45 pure functions (data → panels → sorts → costs → stats → regressions). Where the maths actually lives.
examples/Five runnable scripts, one per extension pattern. Start at 01_baseline.py.
tests/12 acceptance tests: reconciliation to committed outputs, internal identities, and no-op guards on the hooks.

3How extensions plug in

Four attachment points cover every extension in the project. Each one changes a single argument; nothing else about the book moves.

1 · Total-exposure gate

Macro, regimes, ML timing — Vidhi's pattern

gate = my_model_prob.clip(0, 1)   # unlagged
res  = run(exposure=gate)

Your model emits a dated Series of multipliers; the base samples it on the rebalance grid and lags it. Pass it unlagged — the base does the lagging, and double-lagging silently weakens the gate.

2 · Per-currency overlay

Option hedges, filters, manual edits — Theo's pattern

def hedge(weights, ctx):
    return weights * scale   # same shape
res = run(weight_overlay=hedge)

ctx carries the panels, the pre-sizing weights and the signal. Whatever you return is what gets traded, costed and reported.

3 · Robustness sweep

Parameter stress and jackknife — Arjun's pattern

for w in (20, 40, 60, 90, 120):
    run(vol_window=w)
# costs/lag need no rebuild:
base.cost_from_weights(base.weights, 2.0)

Panels are cached, so ~80 rebuilds take under a minute. Cost and lag stresses re-price the stored weight panel instead.

4 · Universe & episode studies

Subsets and single periods — anyone

run(universe=[c for c in names if c != "TRY"])
run().reslice("2008-01-01", "2009-06-30")

reslice re-slices an existing book rather than rebuilding it, so trailing windows still use the data before the start date — what a subperiod study should do.

Reading a robustness sweep

4Assumptions — and their limits

Every choice below is deliberate and inherited by every extension. They are listed so that a result can be argued with.

AssumptionWhy
Signal is forward-implied carry ln(S/F), not an interest-rate ranking It is what is actually tradable — it embeds the NDF and convertibility basis, and needs no onshore fixing to exist. Validated against onshore differentials via a CIP check.
Daily returns, USD-per-FX quotes, 252-day annualisation Excess return = spot log return + previous day's carry accrual — the standard academic construction, and the one behind every committed number in this project.
HKD, DKK, CNY excluded HKD and DKK are pegged: near-zero volatility would hand them enormous inverse-vol weights for a position no one can trade. CNY has no deliverable forward — CNH is the tradable offshore leg.
Quintile sort for the 27-name book, tercile for a single region Keeps at least two names per leg while sorting finely enough to separate high from low carry. Both are config knobs, not hard-coded.
Inverse-volatility legs, 40% single-name cap Beat equal, ERC and mean-variance weighting net of costs in a head-to-head. The cap is what structurally contains extreme names (TRY post-2018) instead of winsorising the signal.
10% vol target, 60-day window, 4× leverage cap Scaled on the book's own trailing realised volatility rather than an ex-ante covariance — with 27 assets a 60-day covariance is noisy and near-singular, and the book only changes monthly.
Signals sampled month-end, lagged one trading day No lookahead. Trailing windows only, everywhere. Overlays inherit the same lag automatically.
Costs = per-currency bid/ask half-spreads, maintained notional rolled via FX swap Charging the full outright spread on the whole book each month would roughly double costs and wrongly kill EM. Every result is reported gross and net.
One common evaluation window, 2007-05 → 2026-06 Every variant covers the same days, so a Sharpe difference is not a sample difference.
Honest limits
  • Daily and USD-per-FX only in v1. Monthly, FCU-per-USD constructions — including Dafu's BER replication — are out of scope by design, and a 1984-start replication cannot run on shared data that begins in 2007.
  • Not a live trading system. Costs come from quoted bid/ask; there is no market impact, no funding curve, no settlement calendar.
  • Option data is mids only. A premium-paying hedge cannot yet be costed, so the option overlay shown here trims positions as a proxy. Buying option bid/ask would change that.
  • The numbers on this page are a snapshot (2026-07-29). If the base changes they must be recomputed — the provenance is recorded in this file's source comment.
  • The base is shared, not frozen. Genuine gaps should be raised rather than worked around: an extension that edits strategy/ to make itself work invalidates everyone else's numbers.
